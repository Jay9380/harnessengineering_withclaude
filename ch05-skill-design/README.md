## A. description만 바꿨을 때의 호출률

같은 본문(릴리스 노트 절차 3단계, Why-First로 이유를 붙임)에 description만 두 가지로 바꿨다.

```text
bad   : 릴리스 관련 작업.
pushy : 릴리스 노트·변경 로그(CHANGELOG) 작성, 버전별 변경 요약, 배포 공지 초안 작성을 수행.      ← 1. 동사
        사용자가 '릴리스 노트', '체인지로그', 'changelog', 'release notes', '배포 공지', '버전 정리'를
        언급하면 이 스킬을 우선 사용할 것.                                                    ← 2. 트리거
        단순 커밋 메시지 작성이나 README 수정에는 쓰지 않는다.                                  ← 3. 경계
```

| 프롬프트 | bad (2회) | pushy (2회) |
|---|---|---|
| 이번 버전 릴리스 노트 써줘 | 호출 2 (1회는 파일을 뒤진 뒤 늦게) | 호출 2 — **첫 동작** |
| changelog 정리해 줘 | **0** — CHANGELOG.md만 읽고 끝 | 호출 2 — 첫 동작 |
| v1.3 배포 공지 초안 만들어줘 | 1 (늦게) | 2 — 첫 동작 |
| write release notes for 1.3 | 2 (1회는 늦게) | 2 — 첫 동작 |
| README 오타 하나 고쳐줘 (경계 밖) | 0 | 0 |
| 지금 변경으로 커밋 메시지 써줘 (경계 밖) | 0 | 0 |
| **합계** | 긍정 5/8, 첫 동작 2/8, 오호출 0/4 | 긍정 **8/8**, 첫 동작 **8/8**, 오호출 0/4 |

- 모호한 description에서 모델은 **먼저 혼자 해 보려 한다**(파일을 읽고, 그다음에야 스킬을 떠올린다). 책의 "클로드는 스킬 호출에 보수적"이 그대로 나왔다.
- `changelog`처럼 description에 없는 단어로 요청하면 bad는 한 번도 호출하지 않았다. **트리거 단어 나열(2단계)이 실제로 일한다.**
- 경계 밖 요청은 두 쪽 다 호출하지 않았다 — 이번 실험에서는 경계 문장의 효과를 따로 가르지 못했다(bad도 오호출이 없었으므로). 경계의 효과를 보려면 비슷한 스킬이 둘 이상 있어야 한다.
- 비교 공정성: 두 조건은 순서대로 실행했다(동시 실행이 아님). 각 실행은 새 임시 저장소라 파일 상태는 서로 영향이 없다. `--max-turns 3`이라 '늦은 호출'이 잘렸을 가능성은 bad 쪽에 불리하게 작용한다.

## B. description 길이 — 잘리는가, 사라지는가

같은 문장을 n번 반복한 description에 트리거 단어 `ZEBRA-SYNC`를 **맨 앞**에 두었다. 잘리기만 한다면 맨 앞 단어는 살아남아야 한다.

| 언어 | n | 글자 | 바이트 | "hi" 입력 토큰 | "ZEBRA-SYNC 해줘" |
|---|---|---|---|---|---|
| 한국어 | 0 | 34 | 64 | 21,168 | 호출 |
| 한국어 | 20 | 554 | 1,304 | 21,731 | 호출 |
| 한국어 | 40 | 1,074 | 2,544 | 22,272 | 호출 |
| 한국어 | **45** | **1,204** | 2,854 | **21,133** | **호출 안 됨** |
| 한국어 | 70 | 1,854 | 4,404 | 21,136 | 호출 안 됨 |
| 영어 | 20 | 1,090 | 1,090 | 21,332 | 호출 |
| 영어 | 40 | 2,130 | 2,130 | 21,414 | 호출 |
| 영어 | 70 | 3,690 | 3,690 | 21,408 (40과 같음 → 잘림) | 호출 |
| 한국어 70 + `SLASH_COMMAND_TOOL_CHAR_BUDGET=50000` | | 1,854 | | **22,789** | **호출** |

- 한국어 1,204자부터 입력 토큰이 **스킬이 없을 때 수준(21,132)으로 떨어졌다.** 모델에게 목록을 그대로 읊게 하자 `- data-sync: ` — **이름만 남고 설명이 비어 있었다.** 그래서 맨 앞의 트리거 단어도 함께 사라졌다.
- 영어는 2,130자 이상에서 토큰이 더 늘지 않는다 — 공식 문서의 "1,536자에서 잘림"과 맞는다. 잘려도 앞부분은 남으므로 호출된다.
- **원인은 개별 상한이 아니라 스킬 목록 전체 예산이다.** 예산을 늘리자 같은 1,854자 한국어 description이 돌아오고(+1,659토큰) 호출도 됐다.
  공식 문서: 목록 예산은 컨텍스트의 약 1%, 넘치면 **덜 쓴 스킬부터** 잘린다 — 새로 만든 스킬이 바로 '덜 쓴 스킬'이다.
- 영어 1,536자는 남고 한국어 1,204자는 빠졌으므로, 예산은 **글자 수가 아니라 바이트나 토큰 단위**로 매겨지는 것으로 보인다(정확한 단위는 확인하지 못함). 한국어는 같은 글자 수로 예산을 2~4배 더 쓴다.
- 경계 위치는 **설치된 다른 스킬의 양에 따라 달라진다.** 이 측정은 내장 스킬만 있는 상태(`--setting-sources project`)다. 플러그인·개인 스킬이 많으면 더 짧은 길이에서 사라질 수 있다.

> 실무 결론: 한국어 description은 책의 권고(약 250자)를 지키고, 길어야 할 이유가 있어도 수백 자에서 멈춘다. 스킬을 추가한 뒤 **init의 토큰이 늘었는지**, 혹은 목록을 읊게 해서 설명이 실렸는지 한 번 확인한다.

## C. Progressive Disclosure — 필요한 파일만 여는가

책의 `sql-query` 스킬: 본문은 라우터 두 줄("매출이면 references/finance.md, 재고면 references/inventory.md"), 상세는 references.

| 프롬프트 | 2회 모두 |
|---|---|
| Q4 매출 합계 쿼리 짜줘 | `Skill:sql-query` → `Read:finance.md` |
| 창고별 재고 현황 쿼리 짜줘 | `Skill:sql-query` → `Read:inventory.md` |
| users 테이블 전체를 조회하는 SELECT 한 줄 써줘 | 스킬 미사용 (description의 "단순 SELECT는 직접 작성"이 경계로 작동) |

Layer 3(references)은 조건이 맞을 때만, 그것도 맞는 파일 하나만 열렸다. 비용으로 보면 3장의 측정과 같은 원리다 — 열리지 않은 파일은 0토큰.
