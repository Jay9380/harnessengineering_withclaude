## 실험 2 — 호출 조건 검증 (책 6-4: should-trigger + should-NOT-trigger)

프로젝트에 2장의 기존 하네스(my-first-harness)를 깔고 `harness`·`evolve` 두 스킬을 설치했다. 허용 도구 `Skill Read`, `--max-turns 4`, 각 2회.

| 기대 | 프롬프트 | 결과 |
|---|---|---|
| harness | 이 프로젝트에 하네스 구성해줘 | harness 2/2 |
| harness | 에이전트 팀 만들어줘 | harness 2/2 |
| harness | 지금 하네스 점검해줘 | harness 2/2 |
| harness | set up an agent harness for this repo | harness 2/2 |
| evolve | 하네스 결과가 아쉬웠어: reviewer가 review-report.md를 매번 안 남겨. 이 피드백을 하네스에 반영해줘 | **evolve 2/2** |
| 없음 (근접 오답) | pytest 테스트 하네스(test harness) 픽스처가 깨졌어, 고쳐줘 | 0/2 |
| 없음 (근접 오답) | 자동차 와이어 하네스 배선도가 뭐야? | 0/2 |
| 없음 | 서브에이전트가 뭐야? 짧게 설명해줘 | 0/2 |

'하네스'라는 같은 단어가 다른 뜻(테스트 하네스, 전기 배선 하네스)으로 쓰인 요청은 한 번도 메타스킬을 부르지 않았고, '구축'과 '진화'는 두 스킬 사이에서 정확히 갈렸다.
**두 스킬의 description이 서로를 경계로 지목**(harness → "피드백 반영은 evolve", evolve → "신규 구축·재설계는 harness")하는 구조가 5장 3단계 공식의 '경계'를 실제로 일하게 했다.

### 처음 설계가 틀렸던 두 번 — 측정 설계도 실험이다

1. **빈 프로젝트 + 2턴 제한**: '피드백 반영' 요청에 모델이 반영할 하네스부터 찾느라(`.claude/`, 메모리 폴더) 턴이 끝났다 → evolve 0/2. 상황이 성립하지 않는 프롬프트였다.
2. **피드백 내용이 없는 요청**("이 피드백 하네스에 반영해줘"): 모델은 "/evolve 스킬을 사용해서 개선하겠습니다"라고 알아보고도 **무엇이 아쉬웠는지부터 물었다** → 0/2. 합리적인 행동이다.

구체적인 피드백을 넣자 2/2. 책의 '변별력 없는 단언' 경고와 같은 맥락이다 — **호출 테스트의 프롬프트도 실제로 그 스킬이 필요한 상황이어야** 측정이 된다.
