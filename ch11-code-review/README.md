# 11장 · 코드 리뷰 자동화 팀 — 1인 리뷰어와 3인 팀을 실제로 비교하기

책 11장은 static-analyzer·design-reviewer·security-auditor·refactorer 4인 팀으로 의도된 버그 4종이 심긴 JWT PR을 리뷰하고,
"Without(단일 리뷰어) 2/4 vs With(팀) 4/4, 시간 62% 단축, 비용 1.8배"를 보여 준다 — 단 **책도 이 수치를 '추정값'이라고 밝힌다**(p.217).
여기서는 같은 모양의 PR을 직접 만들고 실제로 돌려 본다.

```bash
cd ch11-code-review/experiments
./run.sh 2          # 1인·팀 각 2회 (haiku, 약 $0.5)
./run.sh rescore    # 저장된 로그만 다시 채점
```

## 픽스처 — `sample-pr/` (이 저장소에서 작성, 88줄)

책의 버그 4종을 같은 위치·같은 모양으로 심었다(책 예제 저장소에는 PR 원본이 들어 있지 않다).

| # | 버그 | 위치 |
|---|---|---|
| 1 | SQL 문자열 결합 (CWE-89) | `src/api/users.ts` `getUserByEmail` |
| 2 | N+1 — 루프 안에서 `getUserByEmail` | `src/api/users.ts` `inviteMembers` |
| 3 | 경계면 불일치 — API는 `{ accessToken, user }`, 훅은 `User[]` 기대 | `src/api/refresh.ts` ↔ `src/hooks/useUser.ts` |
| 4 | 새 엔드포인트·함수에 테스트 0건 | `tests/`에는 기존 `getUserById` 테스트뿐 |

## 방법

- **1인**: `claude -p`(haiku) 하나가 "컨벤션·설계·성능·보안·테스트를 모두 본다".
- **팀**: 메인(haiku)이 3명(static-analyzer·design-reviewer·security-auditor, 모두 haiku, Read·Grep·Glob)을 한 응답에서 백그라운드로 띄우고 결과를 통합.
  refactorer는 뺐다(패치 생성은 발견 수 비교와 무관).
- 둘 다 같은 형식(JSON 발견 목록)으로 내고, **채점은 코드**가 한다(파일 + 범주/문장 키워드).
- 모델을 모두 haiku로 맞춘 것은 **구조의 차이만** 보기 위해서다(책은 haiku/opus/sonnet을 섞는다).

## 결과 (2026-10-02, 각 2회)

| | 1회차 | 2회차 | 비용(회당) | 시간 | 낸 항목 수 |
|---|---|---|---|---|---|
| 1인 | **4/4** | 3/4 (N+1 놓침) | $0.04 | 23초 | 3~4 |
| 3인 팀 | **4/4** | 3/4 (테스트 누락 놓침) | $0.13~0.20 | 55~137초 | 12~14 |

- **이 크기(88줄)에서는 팀이 더 많이 잡지 못했다.** 합계 7/8로 같고, 팀은 비용 3~5배, 시간 2~6배.
  책의 응용 가이드 자체가 "diff ≤ 100줄 → 단일 서브에이전트, 100~1,000줄 → 팀"이라고 한다 — 결과가 그 표와 맞는다.
- **팀의 이점은 '폭'이었다.** 4개 외에도 JWT `algorithm` 미지정, `inviteMembers`의 권한 확인 누락, 리프레시·액세스 토큰이 같은 비밀키를 쓰는 문제 등 실제로 짚을 만한 항목을 더 냈다.
  동시에 '하드코딩된 경로' 같은 약한 지적도 섞였다 — 통합 단계의 우선순위 정리(책의 P0/P1/P2)가 필요한 이유다.
- **팀 2회차의 누락은 통합 손실일 수 있다.** 세 명 모두 테스트를 1차 관점으로 갖지 않았고(설계 리뷰어의 부가 지시뿐), 최종 목록에도 없었다. 관점을 나누면 **아무에게도 배정되지 않은 관점**이 생긴다 — 책의 4인 팀에는 테스트가 명시적으로 있었다.

### 측정하다 걸린 함정 두 개

1. **채점 규칙 버그**: 팀이 "No tests exist for refresh endpoint …"라고 영어로 찾았는데 규칙이 한글 '테스트'만 봐서 처음엔 3/4로 채점했다. 규칙을 고쳐 다시 채점(`rescore`)했다 — 채점기도 검증 대상이다.
2. **백그라운드 서브에이전트의 tool_result는 '시작 확인'이다.** 로그에서 서브에이전트의 발견을 보려고 Agent 호출의 결과를 읽었더니 셋 다 같은 길이(1,104자)의 접수 메시지였다. 실제 결과는 나중에 완료 알림으로 들어온다.

## 결론

책의 숫자(2/4 vs 4/4)는 300줄 PR, 섞인 모델, 4번째 테스트 관점을 전제로 한 추정이다. **작은 PR에서는 1인이 싸고 빠르고 충분했다.**
팀을 쓸지는 PR 크기와 '놓치면 비싼 관점이 몇 개인가'로 정하고, 팀을 쓴다면 **모든 관점에 담당자가 있는지**(테스트!)를 먼저 확인한다.
