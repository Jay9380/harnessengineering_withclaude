# 12장 · 풀스택 기능 구현 팀 — 경계면은 양쪽을 동시에 읽어야 보인다

책 12장의 핵심 인물은 **boundary-verifier**다. 로그인 기능 하나에도 경계면이 5개(폼↔검증↔API↔JWT↔DB)이고, 실제 서비스에서 드러난 런타임 버그 7개 중
**어느 하나도 TypeScript 컴파일러가 잡지 못했다**(p.224). 그래서 경계면 검증을 전담하는 에이전트가 생산자와 소비자 파일을 **동시에** 열어 7패턴으로 대조한다.
이 폴더는 세 주장 — tsc가 못 잡는다 / 한쪽만 보는 리뷰는 못 잡는다 / 동시에 읽으면 잡는다 — 을 잰다.

```bash
cd ch12-fullstack/experiments && ./run.sh 2     # tsc는 임시 설치, claude는 haiku 약 $0.3
```

## 픽스처 — `login-feature/` (이 저장소에서 작성)

| # | 경계면 버그 (책의 7패턴) | 서버 `server/auth.ts` | 프런트 `web/useLogin.ts` |
|---|---|---|---|
| 1 | 경로 ↔ 링크 | `POST /api/auth/login` | `fetch("/api/login")` |
| 2 | 케이스 변환 | `access_token` | `data.accessToken` |
| 3 | 케이스 변환(필드) | `avatar_url` | `User.avatarUrl` |
| 4 | 옵셔널 필드 | `avatar_url: string \| null` | `user.avatarUrl.split(…)` — null이면 크래시 |
| 5 | 응답 래핑(에러) | 실패 시 `401 { error: { code } }` | `400`만 처리 |
| 6 | 즉시 응답 ↔ 비동기 결과 | `202 { jobId }` | `data.result.status` |

## 결과 (2026-10-02, (A)·(B) 각 2회)

| 방법 | 1회차 | 2회차 |
|---|---|---|
| (0) `tsc --strict` | **오류 0** | — |
| (A) 한쪽씩 보는 리뷰어 2명(서버 폴더만 / 웹 폴더만) 합산 | 3/6 | 3/6 |
| (B) boundary-verifier — 두 파일을 함께, 7패턴 지시 | **6/6** | **6/6** |

- **(0) 책 그대로다.** `fetch().json()`이 `any`라서 strict 모드에서도 타입 오류가 하나도 없다. 타입 시스템은 경계면을 넘어가지 않는다.
- **(A)의 3점은 후하게 쳐 준 점수다.** '경로'는 프런트 리뷰어에게 프롬프트로 서버 경로를 알려 줬기 때문에 잡혔고, '202'는 "`data.result` 존재 확인이 없다"는 **일반적인 방어 지적**이었지 서버가 `{ jobId }`를 준다는 불일치를 찾은 것이 아니다. 서버 리뷰어는 경계면 항목을 하나도 내지 않았다(타이밍 공격, 감사 API 권한 등 자기 쪽 문제만).
  즉 한쪽만 보면 **상대편에 대한 정보가 없는 버그는 원리적으로 볼 수 없다.** 케이스·필드명·null 계열(2·3·4)은 두 번 다 0이었다.
- **(B)는 모든 항목에 양쪽 위치를 붙였다**(`server/auth.ts:20 & web/useLogin.ts:12 | access_token … camelCase …`). 책이 design-reviewer·boundary-verifier에 "두 파일 이상을 동시에 읽어 교차 비교"를 핵심 원칙으로 둔 이유가 숫자로 보인다.

> 책은 boundary-verifier에 opus를 배정한다("두 파일을 동시에 읽고 추론해야 해서 추론 부담이 큼"). 이 작은 픽스처에서는 haiku로도 6/6이었다 — 파일이 커지고 경계면이 많아질 때 모델이 중요해질 것이다.

## 덧붙임 — 이 결과가 말하는 팀 설계

책의 팀은 "QA Phase를 따로 만들지 않고" verifier를 구현 Phase에 상주시킨다. 위 결과는 그 이유를 하나 더한다:
백엔드·프런트 구현자가 **각자 자기 쪽을 아무리 잘 검토해도**(A) 경계면은 남는다. 경계면은 그것만 보는 역할이 있어야 보인다.
